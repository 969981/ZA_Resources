# 锁闪、IV、性格与生成链

> [!warning] 未找到静态字段不等于没有锁闪
> 固定遭遇、礼物、剧情事件可在生成器、事件脚本、主程序条件分支或最终 PID 处理处实施限制。这里没有将任何物种直接认定为“已从 2.0.2 ROM 确认锁闪”。

## 按生成入口分类

| 类别 | 首选来源 | 必须补足 |
| --- | --- | --- |
| 普通野生 | `encount_data_array` + `pokemon_spawner_data_array` | 最终生成结构、PID/EC 和实测 |
| 野生头目 | `oyabun_setting` + `oyabun_waza` | 与普通野生对照的标志及赋值 |
| 固定剧情/礼物 | `script/lua`、`world/ik_scene`、事件入口 | 创建者、调用链、强制禁闪分支 |
| 训练家/固定队伍 | `trainer/trdata/trdata_array.bin` | 队伍数据、是否为捕获目标 |
| 生成的个体值/性格 | `pokemon_data_array` 与 `main.elf` | 六项 IV、性格、特性及最终记录 |

## 复核方法

1. 从匹配的 BFBS 导出 JSON，检索 `shiny / rare / pid / iv / nature / fixed / random` 等**候选词**；词本身并非经确认的字段名。
2. 在 `main.elf` 跟踪对象创建、随机数调用、PID/EC、shiny 判定、IV/性格赋值。记录每个函数的 `main+RVA` 和传入的静态表对象。
3. 对野生、剧情固定、礼物/DLC 特殊场景做差分，记录判定前后值和最终写回字节。
4. 有真实过滤分支或标志且跨样本复现，才能把 `shinyLocked` 填为 true；只做过有限次抽样但从未出闪，不足以证明锁闪。
5. 固定 IV 与随机 IV 范围要分表；分清磁盘上的加密 PKM、解密后的字段以及内存中的临时对象，勿混用字节偏移。

推荐 `shiny_lock_evidence.csv`：
`version,buildId,encounterId,speciesId,formId,scenario,shinyLocked,lockMechanism,functionRva,sourcePath,testCount,evidence`。

推荐 `generation_evidence.csv`：
`sourceId,scenario,ivHp,ivAtk,ivDef,ivSpA,ivSpD,ivSpe,nature,ability,seedOrRngCallsite,pid,ec,source,proof`。

`shinyLocked` 取 `true/false/unknown`，无法验证时必须是 `unknown`。外部 [RotomLabs 闪光机制资料](https://rotomlabs.net/legends-z-a/shiny-rates) 和 [km-editor ZA 研究](https://github-wiki-see.page/m/kotmatrosk1n/km-editor/wiki/Legends-Z-A-Overview) 可辅助选择样本，但不是本仓库运行时证据。
