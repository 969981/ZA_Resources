# 训练家队伍与战斗数据怎么读

## 01. 训练家总表与队伍展开表

| 表 | 行数 | 一行是什么 |
| --- | ---: | --- |
| `trainers/trainer.records.csv` | 3,557 | 一条完整的训练家配置 JSON（含 6 个 `poke` 槽、AI、战斗参数） |
| `trainers/ZA_trainer_parties.csv` | 8,005 | 一个含有效 `devId` 的队伍槽 |
| `battle/waza_attribute.records.csv` | 25 | 一组招式属性的列表 |
| `battle/oyabun_waza.records.csv` | 371 | 一条物种/形态的头目招式配置 |
| `battle/oyabun_setting.records.csv` | 1 | 头目参数根对象 |
| `battle/battle_setting.records.csv` | 1 | 全局战斗设置 JSON |
| `battle/capture.records.csv` | 1 | 捕获配置 JSON |

源路径分别见 `world/ik_data/trainer/trdata/trdata_array.bin` 和 `world/ik_data/field/oyabun/` 等。

## 02. 训练家队伍 CSV 的八列

[完整训练家队伍表](https://github.com/969981/ZA_Resources/blob/docs/za-v2.0.2-obsidian-extraction/Unpack/v2.0.2/romfs/arc/data.trpfs/virtual_converted/_tables/trainers/ZA_trainer_parties.csv)

| 列 | 解释 |
| --- | --- |
| `trainerId` | 训练家配置 `trid`，如 `Ev_m08_7000`、`dim_rank_01_01` |
| `slot` | 第几号队伍槽，整数 1–6；**不等于出场顺序的所有机制** |
| `speciesId` | 队伍对象的 `devId`，与遭遇表的 `devNo` 指代同类编号 |
| `level` | 该成员静态等级字段 |
| `ballId` | 捕获球类型的原始数值；尚未正式链接球名 |
| `rareTypeRaw` | `poke*.rareType` 的枚举原值，**不能先认定等于闪光标志** |
| `natureRaw` | 性格的原始值 |
| `movesJson` | `waza1..waza4` 的原始对象，可能含 `wazaId`、`isPlusWaza` |

**为什么 3,557 条训练家可以展开出 8,005 个队伍槽？** 因为一个 `trainer.records.csv` 记录有 `poke1..poke6`，导出脚本仅对存在 `devId` 的槽位输出一行；所以 8,005 不意味着 8,005 名训练家或 8,005 种宝可梦。

## 03. 一条有意义的真实训练家记录

`trid=Ev_m08_7000` 包含六个有效队伍槽（源 `trainer.records.csv`）。其中：

| 槽位 | 物种 devId | 级别 | 球种 raw |
| --- | ---: | ---: | ---: |
| 1 | 675 | 61 | 10 |
| 2 | 687 | 61 | 10 |
| 3 | 668 | 61 | 10 |
| 4 | 248 | 62 | 10 |
| 5 | 373 | 62 | 10 |
| 6 | 6 | 63 | 10 |

原始记录还包含 `aiExpert=true`、`aiHigh=true`、`megEvolution=true`，以及宝可梦的 `talentValue`、`effortValue`、`wazaId`。

例如第一槽的 `poke1.waza1.wazaId=280`、`waza2=242`、`waza3=418`、`waza4.wazaId=182`，其 `waza4.isPlusWaza=true`。这些是**原始招式编号与强化标志字段**，未与中文名称完成验证关联；不要自行填充猜测的名称。

## 04. 为什么有时招式显示 `{}`？

真实样本 `dim_rank_01_01`：
- `poke1.devId=938`、`level=15`；
- `poke2.devId=406`、`level=15`；
- `waza1..waza4` 显示 `{}`。

**这不等于游戏内一定没有招式。** Reflection 解码时，某个对象本身存在但所有字段都没有显式写入，就可能产生 `{}`。游戏程序可能继续按物种/等级计算默认招式，或其字段保持 FlatBuffers 默认值。必须读对应的 Schema、运行时加载器才能判断。

同理，队伍配置中即使 `poke3..poke6` 存在对象，**只有含 `devId` 的才会被扁平导出为成员**；不要将空对象视为真实队员。

## 05. 训练家想继续看哪些隐藏在原始 JSON 中的信息

`ZA_trainer_parties.csv` 为了方便查看只保留少量关键列。很多重要字段仍在 `trainer.records.csv`：

| 字段例子 | 原始含义提示 | 注意 |
| --- | --- | --- |
| `aiBasic/aiExpert/aiHigh` | AI 等级/开关的候选配置 | 只是字段名提示，不等于所有战斗行为都开启 |
| `megEvolution` | Mega 进化相关布尔配置 | 实际触发还需战斗验证 |
| `moneyRate` | 奖金倍率候选 | 未与奖金额度运算核验 |
| `zaRank` | ZA Rank 相关参数 | 数字→显示段位需映射 |
| `trtype/trtype2` | 原始大整数类别/hash | 不要当作内存地址 |
| `effortValue` | 六项努力值配置 | 与个体值 `talentValue` 不同 |
| `talentValue` | 六项个体数值相关配置 | 缺省字段要考虑默认值 |
| `poke*.item` | 携带道具 ID | 未在简表导出 |
| `waza*.isPlusWaza` | 招式强化相关布尔字段 | 不能从 `{}` 推出 false 的所有业务语义 |

> [!tip] 看完整技能
> 在 `trainer.records.csv` 搜索 `trainerId` 对应的 `trid`。`row_json` 是完整 JSON，可以查看 `poke1.waza1.wazaId`、`isPlusWaza`，比只看扁平表更全面。

## 06. 头目招式与头目生成两回事

**头目招式表** `oyabun_waza`：371 条记录，`devNo`、`formTableList[].formNo`、`wazaNo`。如：
- `devNo=1` 有 `wazaNo=188`；
- `devNo=3` 的形态记录可见 `wazaNo=89`。

**头目配置表** `oyabun_setting`：`MaxTalentValueCount=3`、`StrengthenValue=20`。

**遭遇参数** `ZA_encounters_flat.csv`：可能含 `oyabunProbability`、`oyabunAdditionalLevel`。注意这是三个不同来源/层级。静态“头目技能表”不能直接用来断定每个遇到的头目一定学会哪一招。

## 07. 招式列表不是升级习得表

`waza_attribute.records.csv` 中：
- `WazaCut` → `wazaIdList=[75,163]`；
- `WazaDestruction` → `wazaIdList=[2]`。

表名为 *WazaAttribute*（招式属性分类），不是 `level-up moves`、`TM learnset` 或招式基础威力表。因此不能根据该表反推出物种升级习得招式、所有可学技能或招式伤害。

对“招式的中文名、威力、属性、习得方式”分别建立证据，优先先把 `ik_message/dat/Simp_Chinese/common/wazaname` 与招式 ID 映射闭合。
