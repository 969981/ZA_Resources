## 二、为什么这次能给“确切的中文名”

每个 `.tbl` 有 `AHTB` 魔数、标签条目计数、标签哈希和标签名称；大部分末尾有单独的 `msg_*_max` 标志，**不对应 `.dat` 文本行**。

`.dat` 则含消息数组：每条以 16 位动态 XOR 密钥加密的 UTF-16 文本，解码关键点为：

```text
初始密钥：0x7C89
第 i 行密钥：(0x7C89 + i * 0x2983) & 0xFFFF
每个 UTF-16 单元解码：word XOR key
处理下一个单元：key = ROTL16(key, 3)
```

匹配时不是盲目按“外部图鉴编号”套名字，而是检查 `MONSNAME_000`、`MONSNAME_001`... 标签的数字**确实等于 .dat 的行索引**。实测 `MONSNAME_001=妙蛙种子`、`MONSNAME_003=妙蛙花`，`WAZANAME_001=拍击`。不符合索引的一组会由解析脚本直接报错，避免顺序错位。

| 3 | 妙蛙花 |
| 4 | 小火龙 |

完整 364 张（含两只没有本轮 Encounter 配置、但 Personal 可用的物种） [[22-宝可梦数据档案索引|按物种建的笔记]] 已改用这些真实中文名称。`MONSNAME_000` 解出“蛋”，不是第 0 只野生宝可梦。

## 三、真正的升级学习表：在 Personal，而非 Encounter

过去 `ZA_encounters_flat.csv.wazaListJson` 只是一个遭遇实例的**预置四招**。完整学习集合实际来自：

```text
Unpack/v2.0.2/romfs/arc/data.trpfs/virtual/avalon/data/personal_array.bin
```

FlatBuffers 根向量有 1,445 个 Table；每个 Table：
- field 0：以 **两个 u16** 存 `speciesId,formNo`；
- field 1：`presentFlag`，未出现时当前按 0 记录；
- field 25（vtable 偏移 +0x36）：招式学习向量；
- 向量每条记录 **4 字节**：`u16 moveId`、`u8 learnLevelRaw`、`u8 unlockLevelRaw`。

这一字段布局与 2.0.2 的公开主程序分析一致：[pokeldn 研究中 `main+0xE343A0` 访问 field 25](https://decryptu.github.io/pokeldn/za.html)。研究者还指出通过 Personal 条目获取解锁等级，而不是直接等同“学习等级”；这里的 **main+offset 属于外部分析引用**，还未在本仓库独立复核 ARM64 汇编。

## 五、为什么 Personal 有 1,445 条但“可用”只有 594 条？

`personal_array.bin` 对 0 至 1010 的 speciesId 都有 Table，部分存在多个 form。原始 `presentFlag=1` 的是其中 594 个物种/形态组合，包含 364 个不同物种编号，其余记录也可能有字段或 learnset，但 `presentFlag=0`。

**这不是“图鉴只有 364 种”的充分证明**；若要确定图鉴的可登记成员、图鉴分页和版本限定，还要解 `world/exl/pokedex_contents_data.bin` 与 `pokedex_sp_distribution_data.bin` 的业务 Schema。它们之前只到 `STRUCTURE_ONLY`。

## 六、图鉴说明文字和“图鉴编号”不能画等号

`zukan_comment_A/B` 消息标签形如 `ZKN_COMMENT_A_001_000`；可以用前一个数字归类到 `speciesId=1` 的候选描述，**但末尾后缀的含义（形态/版本/其他条目）没有完整证明**。笔记会保留源标签而不自行重命名。

例如 `ZKN_COMMENT_A_001_000` 对应妙蛙种子相关文本，标签一致性是一个数据证据；正式地区图鉴顺序仍要以 EXL/主程序索引为准。
